El concepto

Qué es y por qué existe

El problema, el enfoque y el alcance real del proyecto.

Turnero es una aplicación web monolítica en Flask y SQLite que organiza la atención de una sucursal con tres interfaces sobre la misma base: kiosco de autoatención con RUT y QR, consola de ejecutivo con login y escaneo, y display público que se actualiza por Server-Sent Events. Implementa una cola FIFO global, códigos correlativos por trámite (A, B, C) y una máquina de estados de cuatro fases.

Apunta a equipos que quieran entender o extender un sistema de turnos sin una plataforma comercial, y funciona como pieza de portfolio por la separación en capas. No es multi-sucursal, no tiene administración web, audio ni cancelación de turnos, y el bus SSE vive en memoria, lo que obliga a un solo worker. Los códigos por COUNT + 1 pueden colisionar si se borran turnos, limitación declarada junto a otras nueve.

Cómo leer esta ficha

Los tropiezos salen de la bitácora y de las versiones tempranas. La evaluación usa seis criterios fijos, de 1 a 5, y no premia la espectacularidad: premia que el proyecto se pueda reproducir y entender.

01 — La idea

Tres pantallas, un solo flujo

El kiosco emite el turno, el ejecutivo lo llama y el display lo muestra. Todo con una base SQLite y sin infraestructura pesada.

El problema

Los sistemas de turnos suelen ser cajas negras con licencias, servidores y pantallas propietarias. Para una oficina pequeña, ese costo no se justifica.

La solución

Una app Flask con tres interfaces: kiosco para el usuario, consola para el ejecutivo y display para la sala. SQLite guarda los turnos y SSE empuja los cambios al instante.

02 — El recorrido

Cómo funciona, paso a paso

Del RUT al llamado, sin recargar la página.

01

El usuario se identifica

El kiosco valida el RUT chileno y genera un turno con QR.

02

El turno entra a la cola

SQLite registra el turno y su estado; la cola se ordena por prioridad y llegada.

03

El ejecutivo llama

Desde su consola selecciona el siguiente turno y lo marca como atendido.

04

El display se actualiza

SSE empuja el nuevo llamado a la pantalla de la sala sin polling.

Tropiezos

Los tropiezos, documentados

Lo que no funcionó en las primeras versiones, con la corrección aplicada.

v1.0 · API pública

El qr_token viajaba al display

El endpoint /api/turnos/display reutilizaba to_dict() e incluía el token que permite iniciar la atención. Se creó to_display_dict() para las respuestas públicas; los eventos SSE siguen emitiendo el turno completo y la fuga quedó documentada.

v1.0 · validación

RUT validado solo en el navegador

Un curl con RUT inválido creaba el turno porque la validación vivía en kiosco.js. validar_rut() con módulo 11 se movió a turno_service y la API responde 400; el cliente conserva la comprobación solo como feedback.

v1.0 · numeración

Códigos de turno que colisionan

codigo = prefijo + (COUNT(tipo) + 1) retrocede al borrar turnos y la restricción unique rechaza el nuevo código. Se documentó como limitación y se recomendó reiniciar la base; falta una secuencia persistente por tipo.

v1.0 · presencia

Módulos fantasma en el display

logged_in es un booleano persistido que solo se limpia con logout explícito, así que cerrar la pestaña dejaba el módulo visible. Se documentó el cierre de sesión y se agregó el evento ejecutivo_logout, sin TTL ni heartbeat.

Preguntas

Lo que suelen preguntar

¿Qué es Turnero?

Una aplicación Flask con SQLite que gestiona turnos en una sucursal: kiosco para que el cliente se asigne un número, consola para el ejecutivo y display público actualizado por SSE.

¿Soporta varias sucursales o administración web?

No. Hay una sola instancia y una sola cola; trámites, módulos y ejecutivos se gestionan por seed o SQL, sin panel de administración ni cancelación de turnos.

¿Cómo se ejecuta?

Se crea un venv, se instala requirements.txt y se lanza python app.py, que escucha en 0.0.0.0:5000 y siembra la base si está vacía; el QR requiere HTTPS o localhost.

¿Qué se puede reutilizar?

La máquina de estados con servicios separados de las rutas, la validación de RUT en servidor y el patrón de serialización distinto para público y autenticado.
